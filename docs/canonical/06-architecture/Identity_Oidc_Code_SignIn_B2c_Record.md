## 1. Scope ekzakt (dhe çfarë NUK është)

**Është:** zgjerimi i authority-t ekzistues nga OAuth 2.0-only (B.2b) në **profilin OIDC Authorization Code + PKCE, provider-side**, mbi login/consent + PKCE ekzistues:

1. Kërkesa me scope `openid` → login/consent ekzistues (i pandryshuar) → kod → shkëmbim në `/connect/token` → **access token + ID token i vlefshëm** (nënshkruar me credentials REALE të B.2a).
2. **`nonce`**: kur dërgohet në kërkesën OIDC, ruhet nga OpenIddict dhe lidhet EKZAKT me ID token-in e atij flow-i; mungesa lejohet për code flow (OIDC Core §3.1.2.1 — `nonce` OPTIONAL në code flow); nuk shpiket rregull universal ndalimi. `state` i pandryshuar (kontrata B.2b).
3. **UserInfo minimal** (`/connect/userinfo`, GET + POST, OIDC Core §5.3): përgjigjja e suksesit përmban VETËM `sub`; pa cache (`no-store`).
4. Claims minimale: `sub` + claims të protokollit; **zero** profile/email/phone/address/roles/permissions/business IDs/security stamp/claims të brendshëm të përdoruesit.
5. Discovery/JWKS shpallin VETËM aftësitë reale: `openid`, `id_token_signing_alg_values_supported` (algoritmi REAL i firmës), `userinfo_endpoint`, `claims_supported` = vetëm claims protokolli. *(Vlerat konkrete të vëzhguara — `RS256`, `[aud,exp,iat,iss,sub]` — janë inventar i vëzhguar; testet pinojnë NËNBASHKËSINË e lejuar dhe përputhjen me `alg`-un real të ID token-it, jo listën literale.)*

**NUK është dhe mbetet OPEN:** full OIDC conformance/certification; integrimi real Angular dhe vendimi BFF/SPA/klient; refresh rotation/reuse; MFA/verification/recovery; logout/session/device revocation; offline auth (`PLANET_PILOT_BLOCKER`); B.3 projection/freshness/reconciliation; audit identity; runtime credential expiry; custody/provisioning (ADR-025/026); implicit/hybrid/password/client-credentials/device/PAR/`offline_access` (të papranueshme); user provisioning/signup/role CRUD. Konsumatori sintetik i testit verifikon kontratën — **nuk është aplikacioni final Angular**.

**Acceptance (IASD §9):** E2 = evidencë shtesë VETËM për profilin OIDC provider-side (IMPLEMENTED IN BRANCH / PENDING_INDEPENDENT_REVIEW); E3 mbetet OPEN; E5 mbetet PARTIAL.

## 3. Ownership / arkitektura (ADR-029) — rruga e re UserInfo

`UserInfoController` (Identity/Presentation, thin, `[ApiController]`, `ApiExplorerSettings(IgnoreApi = true)`) → **`IMediator`** → `GetUserInfoQuery`/`GetUserInfoHandler` (Identity/Application, `Features/GetUserInfo/`) → port neutral `IUserInfoSubjectResolver` (Application) → adapter `OpenIddictUserInfoSubjectResolver` (Identity/Infrastructure).

- **BaseApiController** minimal, MODULE-LOCAL në Identity/Presentation (vetëm `IMediator`), pa varësi nga PlatformStatus dhe pa shared framework (guard: dy owner-a module-local, secili `ControllerBase` direkt).
- **Përjashtimi i datuar `IMediator` (04.09.2026)** mbetet VETËM për login/consent ekzistues; **nuk zgjerohet** te UserInfo (guard-i i controller-it të hollë mbulon edhe `UserInfoController`).
- **Autentikimi i UserInfo:** principal-i vjen VETËM nga skema e SERVER-it OpenIddict (`AuthenticateAsync(OpenIddictServerAspNetCoreDefaults.AuthenticationScheme)`) — rezultati i validimit REAL të bearer-it që OpenIddict e kryen PARA passthrough-it; **jo** `HttpContext.User`, **jo** cookie, **jo** skema default e API-së, **jo** parametra, **jo** dekodim tokeni. Fail-closed: endpoint tjetër / lloj tjetër tokeni / pa `openid` / subjekt bosh → refuzim.
- **Passthrough:** `EnableUserInfoEndpointPassthrough` + `SetUserInfoEndpointUris` = **owner-only** (Identity.Infrastructure; guard `InteractionOwnerOnlyMembers`); `EnableTokenEndpointPassthrough` mbetet **I NDALUAR kudo**.
- **JOSE:** gate-i i serverit (`ValidateServerOuterHeader`) është tani **endpoint-aware**: `invalid_grant` te token endpoint-i (kodi), `invalid_token` te UserInfo (bearer) — kontrollet JOSE identike, asnjë dobësim.
- **Pipeline:** rendi i middleware-ve i pandryshuar; predicate-i i cookie-binding (`/identity/*`, `/connect/authorize`) **nuk** zgjerohet te UserInfo; kufiri 503 (`/connect/*`) mbulon UserInfo (JSON `temporarily_unavailable`, `no-store`, trup gjenerik).
- **Paketat:** `Mediator.Abstractions` (pin-i EKZISTUES 3.0.2, CPM) shtuar në Identity Application/Presentation; `Mediator.SourceGenerator` mbetet vetëm në API host; zero paketë/version tjetër; OpenIddict 7.6.0, Identity EF 10.0.10 të pandryshuara. Lockfile-et: vetëm delta e derivuar (Mediator.Abstractions 3.0.2 + `Microsoft.Extensions.DependencyInjection.Abstractions` 8.0.0 transitive + hartat e varësive të nyjeve Project) — e deklaruar paraprakisht dhe e verifikuar me `--locked-mode`.

### 13.2 B — privatësia e log-eve të HOST-it (para shkrimit te sink-et)

**Burimi i evidencës (i ruajtur si i tillë):** Codex identifikoi rrugën statikisht (pa riprodhim runtime); Fable raportoi më pas dy event-e `Information` nga `Microsoft.AspNetCore.Hosting.Diagnostics` me access token-in e plotë për një kërkesë UserInfo me kredencial në URL, ndonëse kërkesa u refuzua me 400. Asnjë vlerë ose dump nuk kopjohet këtu.

**Fakti i pinuar (ASP.NET Core 10.0.10, `HostingApplicationDiagnostics`):** EventId 1 `RequestStarting` dhe 2 `RequestFinished` janë `Information`, mbartin URL-në e plotë — `QueryString` në mesazhin e formatuar DHE si çelës më vete në structured state — dhe janë të mbrojtura nga `IsEnabled(Information)` në thirrës, pra me dysheme `Warning` as objekti i state-it nuk krijohet; kategoria nuk emeton asnjë event `Warning+` per-request (vetëm në startup); scope-i i kërkesës mban `RequestId`/`RequestPath` pa query. Rregullimi i C1 për `code_verifier` te `OpenIddict*` mbetet i vlefshëm dhe NUK e mbulonte këtë rrugë.

**Fix:** `Microsoft.AspNetCore.Hosting.Diagnostics` bëhet target i DYTË i së njëjtës politikë (dysheme `Warning`) — vepron PARA shkrimit te çdo sink të regjistruar përmes `ILoggerFactory` (sink-et jashtë filtrit të tij = jashtë kufirit, §13.1). **Trade-off i deklaruar:** humbet telemetria e përmbledhjes së kërkesave (request summary) e kësaj kategorie dhe event-i `Information` i kërkesave të patrajtuara (EventId 16, vetëm path); event-et `Warning`/`Critical` të saj ruhen (sipas burimit të pinuar asnjë event `Warning+` per-request — vetëm në startup) dhe çdo kategori tjetër ruhet. Zero `ClearProviders`/`LogLevel.None` në production, zero filtër mbi `Microsoft.*`, zero dobësim PKCE/transporti.

**Kontroll RED (`Kontroll_RED_pa_politiken_canary_i_padhemshem_del_ne_te_dy_kategorite_target`, diskriminues, ZERO material autentikimi):** host me regjistrimin e politikës të HEQUR (descriptor-i i `PostConfigure` i identifikuar sipas tipit; parakushti pohon se ishte i instaluar), dalje të kontrolluara: (a) canary `Information` përmes fabrikës reale kapet në të dy target-et; (b) kërkesë REALE e padëmshme (discovery) me canary në query → rekord `Information` i host-it me EventId 1/2, marker-i në mesazh DHE në structured state (`QueryString=`); (c) event-e reale `Information` të `OpenIddict*`. Zëvendëson kontrollin RED të C1, që riprodhonte rrjedhjen me material real drejt provider-ave të zakonshëm.

**Prova GREEN (`Politika_e_log_eve_ndalon_materialin_e_flow_it_dhe_URL_ne_ne_sukses_refuzim_transport_dhe_deshtim_DB`):** mbi konfigurimin real të filtrit dhe politikën production, me DALJE TË KONTROLLUARA (provider-at e zakonshëm hiqen VETËM në host-in e testit dhe zëvendësohen nga dy sink-e pasive në memorie — izolimi i destinacionit nuk ndryshon filtrin as atë që collector-i pohon): politika është EFEKTIVE PARA kërkesës së parë (`IsEnabled(Information)` = `false`, `IsEnabled(Warning)` = `true` për `OpenIddict*` dhe host-diagnostics); canary GREEN (target-et vetëm `Warning`/`Error`, kategoritë e tjera edhe `Information`); e PARA kërkesë HTTP e host-it (discovery me canary në URL) nuk prodhon asnjë rekord me marker-in; flow OIDC POZITIV + UserInfo 200; refuzim REAL i protokollit (400); transport i refuzuar me kredencialin REAL në URL dhe në trup (400); dështim REAL i infrastrukturës (503). Pohimet: zero rekord nën `Warning` në asnjë kategori target (pra zero `Request starting/finished`); asnjë nga vlerat sintetike reale (verifier, kod, access token — përfshirë atë të dërguar në URL — ID token, kodi/verifier-i i refuzuar, kredenciali, subjekti, cookie) në asnjë sipërfaqe të kapur; collector-i i gjallë (`Information` jashtë target-eve, `Warning` i kufirit 503). Dështimet raportojnë vetëm etiketën e artefaktit, `Category#EventId[Level]` dhe numrin.

**Mbulimi i kapjes (i kualifikuar):** mesazhi i formatuar, structured state (çift-çift), scopes (`ISupportExternalScope`), exception-i i JASHTËM (tip + mesazh + stack); **inner exceptions NUK mbulohen** — kufi i deklaruar, jo “çdo sink i mundshëm”.

E MATUR me një probe të përkohshëm (i fshirë menjëherë, kurrë në repo): `state`, `nonce`, `client_id` = 1 rekord secili në atë kategori; `code`, `verifier` = 0. ### 13.3 C — recovery me përgjigje reale në ÇDO degë

Ruhen: dy fault-et test-only në pikën reale `SaveChanges` (`Added` = issuance, `Modified` = shlyerje), kodi i lëshuar PARA armatosjes, `Fired == true`, çarmatosja para recovery-t, pohimet e dështimit fillestar (503/JSON/`no-store`/zero token/zero detaj për issuance; refuzim fail-closed `invalid_grant` pa token për shlyerjen). Hiqet modeli `retryToken = null` për çdo status jo-200. Retry-i me të NJËJTIN kod (`AssertRetryBranchAsync`): **400** → JSON i parsuar, `error=invalid_grant`, zero `access_token`/`id_token`, zero echo (kod/verifier/subjekt); **200** → access token DHE ID token jo-boshë, pastaj ripërdorimi i dytë **400 `invalid_grant`** me trup të lexuar dhe pa token-a; **status tjetër ose JSON i pavlefshëm → dështim** (`Assert.Fail`/`JsonException`), asnjë degë e heshtur. Recovery me flow të RI → 200 me access DHE ID token në të DY testet.

**E vëzhguar në run-in final (raportohet, nuk pinohet):** *(a)* issuance → retry = 400 `invalid_grant`; *(b)* shlyerje → retry = 200 (access + ID) pastaj ripërdorim = 400 `invalid_grant`. **Garancia e pinuar:** vetëm bashkësia {400 pa token, 200 me të dy token-at pastaj 400}. Injektimi ndodh në `SavingChanges` (PARA shkrimit) — **nuk është provë rollback-u fizik as e pasigurisë post-commit**; matrica e §6 (rreshti 8) u rakordua me këtë kufi.

### 13.4 D — transporti UserInfo i plotë dhe `no-store`

**Actual para C2 (i nxjerrë nga burimi i OpenIddict 7.6.0, jo i ekzekutuar mbi head-in e mëparshëm):** `ExtractAccessToken` lexon `Authorization` si string të BASHKUAR (vlera të shumëfishta me presje), merr gjithçka pas `Bearer ` dhe nuk refuzon kurrë — dy header-a `Bearer` bëheshin një token `A,Bearer B` → **401 `invalid_token`**; `Basic`+`Bearer` → pa token nga header-i → 401; refuzimet e pipeline-it të serverit nuk mbartnin `Cache-Control` (`AttachCacheControlHeader` nuk regjistrohet për UserInfo në 7.6.0). Pra kontrata “400 `invalid_request`” për transport të paqartë ishte e pambyllur.

**Fix:** `UserInfoTransportGuard.ClassifyAuthorizationHeader` (PUR) mbi vlerat ORIGJINALE të header-it: `Absent` / `SingleBearer` / `OtherScheme` / `Ambiguous`, ku `Ambiguous` = më shumë se një vlerë jo-bosh (të përsëritura ose skema të përziera) OSE një vlerë e vetme që është LISTË e bashkuar — ≥ 2 segmente të ndarë me presje në formën `skemë SP kredencial` (nënshkrimi i bashkimit RFC 9110 §5.3) — e kontrolluar PARA skemës, pra `Basic …, Bearer …` dhe `Bearer …, Basic …` njësoj (gjetje e review-it të brendshëm: versioni i parë e lexonte skemën e parë dhe do të kishte dhënë 401 për `Basic` në krye). Kufij të deklaruar: auth-param-e me presje të një skeme tjetër (`Digest a="1", b="2"`) = skemë tjetër → 401; `Bearer a,b` = kredencial i vetëm i pavlefshëm → 401 `invalid_token` (biblioteka); rreshta të përsëritur BOSH injorohen (nuk janë kredencial). `Ambiguous` → `context.Reject(invalid_request)` në të njëjtin handler PARA `ValidateAccessTokenParameter` (pra para autentikimit), pastaj kontrollet ekzistuese sipas PRANISË në query/form; asnjë parser JWT, `Bearer` case-insensitive. Header-at `Cache-Control: no-store`/`Pragma: no-cache` vendosen përmes rrugës STANDARDE të OpenIddict — regjistrimi i descriptor-it `AttachCacheControlHeader<ApplyUserInfoResponseContext>` (rendi 101 000, para `ProcessChallengeErrorResponse` ku përfundon dërgimi i gabimit) në owner-in Infrastructure; rruga e suksesit (passthrough) i vendos vetë te controller-i. Kufizimi NUK zgjerohet te `/connect/token`.

**Testet:** `UserInfo_refuzon_header_Authorization_te_perseritur_te_bashkuar_ose_skema_te_perziera_me_400_no_store` — 7 forma (i përsëritur identik, i përsëritur i ndryshëm, i bashkuar `Bearer, Bearer`, i bashkuar `Basic, Bearer`, i bashkuar `Bearer, Basic`, dy vlera `Basic`+`Bearer`, dy vlera `Bearer`+`Basic`) × GET/POST → 400 `invalid_request` (në `WWW-Authenticate`), **trup BOSH i pinuar** (refuzimi i hershëm i pipeline-it të serverit në 7.6.0), `no-store` + `no-cache`, zero subjekt/echo i asnjë token-i në challenge; kontrolle të ruajtura (GET dhe POST): `bearer` me shkronja të vogla → 200 me `sub`; `Basic` i vetëm → 401 challenge bazë `Bearer` pa kod gabimi (RFC 6750 §3); NJË header me token të pavlefshëm → 401 `invalid_token` (jo 400); pa header → 401; klient pa `openid` → 403 me `no-store` (rruga e controller-it). Dështimet raportojnë vetëm etiketa, kurrë vlera. `UserInfo_pranon_vetem_bearer_header…` dhe blloku i transportit të paqartë te `UserInfo_nuk_zgjedh…` tani pohojnë `no-store`/`no-cache` edhe mbi 400-at dhe mbi 401-in pa kredencial. Header-at dërgohen BRUTO (`TryAddWithoutValidation`, një hyrje për vlerë) — cilido përfaqësim që arrin serverin (vlera të ndara ose të bashkuara) klasifikohet `Ambiguous` sipas ndërtimit.
